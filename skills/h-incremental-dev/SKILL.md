# 增量开发/变更工作流

以**项目规范与 skill 最佳实践为基底**（AGENTS.md 硬规则、engineering-philosophy、语言 craft）——讨论与实现都不偏离既有约定。

## 流程

**两大块：规划（先确认需求，其余并行）→ 执行（变更流程）**。

### 规划块（达成整体共识前都在此循环）

**问问题规范（贯穿纪律）**：

- **决策树 + frontier**：把需求/设计组织成**决策树**（决策 → 依赖它的子决策）；**每轮问整个 frontier**（前置已决的全部决策，编号 + 推荐答案），回答后重算 frontier 再问下一轮——依赖未决的推迟到后轮、环境可查的事实自行查取（派子代理）不问用户、必然派生项不是决策不进树；frontier 清空且用户确认共享理解后收敛
- **先概念后实现**：先确认概念层（功能是什么/做什么/领域语义/术语/数据含义），再设计层（UI 形态/流程形态），最后实现层（技术方案：枚举/参数/组件）——每层确认后再进入下一层
- **确认前先输出前置内容**：该决策点相关的目标/意图、UI 设计图（字符画）、流程设计（流程图）、关键思路——用户看到完整上下文后再 ask 对账
- **确认驱动树演进**：每确认一点，更新决策树（确认引出的派生决策加入，已被决策覆盖的移除）
- 每个决策点**必带推荐答案**；选项**短标签 + 一句理由**
- **合理运用 ask 工具**：决策用 ask（选择形式、标推荐）让用户拍板——做选择题比打字对用户更轻松；复杂场景先文字说明再给选项
- **事实查环境**（代码/文档/tools 可查的查）——问的是决策，不是复述
- 问题涉及 UI 时**必须绘制 UI 展示**（字符画）；UI 有变动时绘制**原始与新的对比**（用户一眼看出改了什么）

**1. 需求与意图（goal）——唯一必须先完成，其余规划项依赖它**

- **先明确整套功能的意图**：这套功能**为了做什么而实现**（解决什么问题、服务什么目标）——意图优先于一切细节
- 问出需求**背后的意图**（"为什么做"）
- 边界：做什么、不做什么
- 与既有行为的差异（重新审视现有功能时：现状为什么这样 vs 新主张的取舍）
- **核对理解一致性**：复述你的理解（含推断），让用户确认是否一致
- **主动批判性挖掘**：不止核对与质疑——主动发现用户没发现的点（需求盲区、技术风险、未考虑的决策/边界），主动提出建议与计划——有主见，不当应声虫（头脑风暴：先发散提方向，再收敛确认）

**2. 设计草图**（有 UI 时）

- **UI 草案（字符画）**：界面布局/控件/交互形态的 **ASCII 草图**，随回复展示
- **功能流程图**：数据流/状态流转/用户操作路径（` ```mermaid ` 或文本图）

**3. 技术方案**

- 方案取舍摆明（真实权衡）、影响面、涉及模块/文档/测试
- **从整个项目/长远考虑**——实现可能改动架构，架构变动的方案要摆明（取舍/影响面）
- **一次性给全完整方案集 + 明确推荐**（含全部选项的取舍与推荐理由）——残缺选项或无推荐视为未完成
- **方案附决策依据摘要**：推荐方案说明推理链——为什么选它、考虑过哪些替代、排除其他选项的理由——用户看清决策依据后确认或反驳（不是黑箱结论）
- **关键取舍以问题形式逐一提出**：每个取舍点转成问题让用户回答（如"用 A 还是 B？""参数入口选哪个？"）
- **方案不确定时联网调研**：库 API、生态惯例、最佳实践——以官方文档/权威来源为准，**验证时效性**（远古文章/被新技术取代/久未维护）（决策依赖"大家都怎么做"且有分歧时可查证统计/共识）
- **批判性评估每个方案**：摆明缺陷/风险/副作用，同时给推荐理由——"这个方案真解决根本问题吗"
- 自行判断相关代码：发现同类问题一并纳入

**回环纪律**：任何变动（无论大小）→ **回到规划块对应项重新确认**——触及概念/归属/意图的变动回到**需求与意图（第一项）**重新明确；触及设计/方案的回到对应项（设计草图/技术方案）——**每处改动都经确认后实施**。实现中的**非决策项**（必然派生/无取舍的实现选择）自行处理，有取舍或影响面的变动才回环确认。

**确认驱动设计更正——增量展示**：整个项目的设计只在宏观层画一次（整体结构/数据流）；细粒度变动只展示**相关与变动的部分**（"原始 vs 新"对比该片段）。

**自检遗漏**：每轮确认后按**设计维度清单**反向扫描待确认点——功能行为 / UI 控件与布局 / 数据流与中间产物 / 参数与默认值 / 错误与异常路径 / 兼容与迁移 / 性能边界 / 配置持久化——未覆盖的决策点加入清单（收敛判据的前提是清单列全）。

**验收标准随规划产出**：规划达成共识时同步产出验收标准（与规划强关联——每个决策点对应验收表述），执行后照单验收。

**spec 随规划产出**：规划共识达成时，按 `references/SPEC-FORMAT.md` 把设计意图固化进 spec 文档（惯例 `docs/specs/`，实际位置以 AGENTS.md §2 导航为准）——需求、为什么这么做、边界不活在对话里（易失）；实现与验收对照 spec，需求变化回规划 + 更新 spec。

**分段执行**：规划共识产出 spec 后可暂停存档——实现可在后续会话进行（新会话按 AGENTS.md §2 导航定位 spec 继续实现，无需重新规划；spec 有 gap 时按回环纪律补规划）。

### 执行块（达成共识后）

**开始执行前显式征得用户同意**（"确认开始实现？"）——规划确认与开工许可是两步；得到同意后创建任务、开始实现。

1. **创建/更新任务追踪**（按项目追踪机制，如 backlog；无则建，有则续用——规划变动时更新任务）
2. **实现** + 同轮同步文档（变更→文档映射按 `h-agent-docs maintain` 流程）——**任何阶段（实现中/验收前）发现需求/方案问题或意图变动 → 随时跳回规划块修正**（实现后/使用中发现不合适同样回规划块；验收通过后的变更属新一轮功能迭代）。**实现后自证**：按项目测试约定（项目采用 tdd 则 tdd；无约定则冒烟验证改动路径）跑相关测试/冒烟，提供验证证据再交付验收——测试纪律本身是项目决策，不默认强制
3. **等待验收**：实现完成后**汇报时显式列出验收点**（用户测什么；**对照规划产出的验收标准自审**——每个决策点是否覆盖）；挂起期间**合适时机主动提醒**（新对话/问进度/相关话题/会话末），让用户及时验收
4. **验收通过** → 按项目机制收尾任务（检查验收标准 → 标记完成）
5. **验收不通过** → 判断原因：
   - 实现缺陷 → 修正实现，回到执行第 2 步
   - **预期未完全明确 / 用户发现设计有误** → **回到规划块**（重新澄清意图、修正设计）→ 确定方案后**更新任务或追加进展** → 实现 → 等待验收（循环）
