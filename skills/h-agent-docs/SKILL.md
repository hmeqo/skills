# agent-docs — 文档体系生成和管理

为任意项目生成**分层式 agent 文档体系**（入口 AGENTS.md + 文档 docs/：CONTEXT 术语、architecture 全览、adr 决策），并自动注入工程哲学（代码原则、概念抽象分层、契约式失败、各语言规范）。

**哲学注入**：所有生成内容默认遵循 `references/engineering-philosophy.md`（跨语言原则）与对应语言 `references/*-craft.md`。生成时把这些规范作为 AGENTS.md"硬规则"的默认素材来源。

**验收原则（贯穿所有流程）**：任何流程产物（文档体系/变更记录/重构）以**用户验收通过为完成标志**；验收不通过（不符合预期/方向变化）→ 回到对应步骤迭代（修正任务/追加进展），直到验收通过。任务追踪状态由项目自身的追踪机制管理（AGENTS §5 定案，见机制职责总览）。

## 调用方式

| `agent-docs` | 为当前项目生成文档体系（AGENTS.md + docs/：CONTEXT/architecture，adr 按需）；指定其他项目按对话上下文（用户给出的路径/描述） |
| `agent-docs` 维护 | 文档漂移/升级后重构（审查+修复一体）：对照本 skill 最新设计规范（哲学注入清单/结构模板/输出清单）检查已生成项目的缺漏与结构不一致；直接修复（不输出只读清单）；未定案问询项用 ask 重新决策；按项目追踪机制登记（**遵循外部动作纪律，见哲学注入清单**），验收后收尾 |

## 机制职责总览

| 机制      | 职责                                    | 触发                    | 落点                                             |
| --------- | --------------------------------------- | ----------------------- | ------------------------------------------------ |
| spec 产出 | 规划共识固化需求/意图/边界/验收（按需） | h-planning 规划共识     | 项目指定的追踪系统（Q1 定案）                    |
| 决策存放  | 决策与理由唯一记录                      | 用户主动要求（Q3 定案） | 无（默认）/ backlog / docs/adr/ / 主题文档决策节 |
| 导航权威  | 文档位置查找                            | 会话加载 AGENTS.md      | AGENTS.md §2                                     |
| 维护      | 文档漂移/升级后重构（审查+修复一体）    | 显式调用（漂移/升级后） | 按上表映射的目标文档                             |

**追踪/决策机制默认不建，用户主动要求才建（Q1/Q3 定案）——下文所有 Q1/Q3 相关表述以此为准，不重复。**

## 生成流程

### 第一步：调研先行

**先识别项目形态**（不假设）：

- 有代码且结构规范 → 调研提取（完整文档体系）
- 无代码（只有文档/杂物）→ 只建骨架（AGENTS.md 硬规则：哲学注入）；内容文档（CONTEXT/architecture/导航）演进中懒建
- 有代码但杂乱（临时/不成结构）→ 只建骨架 + 提示"结构未整理，内容文档待整理后建"；不基于杂乱代码提取导航/架构（防止固化错误结构）

用 scout 子代理并行分区只读调研，每区输出结构化规格要点：

- 分区建议：核心领域模型 / 基础设施与外部系统 / UI 全貌 / 算法与特殊子系统；非代码项目（纯文档/配置/技能集合）按模块或主题分区（如按 skill、按 references）
- **工具链与自定义命令确定（必做）**：读锁文件/包管理器配置/测试与构建配置（pyproject.toml、uv.lock、package.json、pnpm-workspace.yaml 等）确定项目实际工具链（包管理器/运行器/测试框架/构建工具/格式化）；读脚本配置（package.json scripts、pyproject scripts、Makefile、shell 脚本、CI 配置）确定**项目自定义命令**（如 `uv run manage`、`./manage.sh`、CI 钩子），与用户确认后分别写入 AGENTS.md 工具链节与命令节
- **版本控制检查**：发现项目无 git（未初始化）或环境无 git（git 命令不可用）时提醒用户现场决策：初始化（`git init` + 按 Q2 定案提交约定）还是跳过 git 相关配置（不注入 git 纪律，Q2 不适用）；有 git 则跳过此检查
- 每个 scout 必须输出：**模块→文件导航**（非摘要）、关键决策与理由、依赖方向、坑与遗留问题、领域术语
- **调研确认（对账 + 决策问询）**：
  1. **对账（事实层）**：全部调研产出一次列全（编号 + agent 的理解：工具链/导航/决策/坑/术语），用户逐项确认或纠正；无决策依赖，一轮对账即可；推测标 `[INFERENCE]` 重点核对
  2. **决策问询（决策层）**：对账中暴露的歧义/取舍（工具链歧义、术语混用裁决、架构问题处置、坑的处理）→ grilling 式问询（选项 + 推荐；有依赖关系时用决策树）
     全部确认后写入

### 第二步：定结构（先问用户）

**问询方式：用 ask 工具（选择形式，标推荐）让用户拍板；复杂场景文字说明 + 选项结合**。

**Q1 变更记录载体**（决定 AGENTS.md §4/§5 维护机制形态；**维护者始终是 agent**（同轮变更纪律强制追加）；**默认不建（见机制职责总览）**）：

- **无变更记录**（推荐）：默认形态。一次性实验/纯工具仓库不需要维护机制；AGENTS §5 标注"无"（形成行为契约的才记）
- **用户指定外部追踪**：**确定具体机制**（backlog CLI / GitHub Issues / 其他，选定后需问清用哪个），记录本体在外部系统；AGENTS 按该机制生成**追踪工作流说明**（该机制如何参与变更流程：登记/更新进展/验收后收尾的具体步骤；backlog 与 GitHub 工作流不同，按选定机制写）。追踪条目的创建/更新/关闭遵循外部动作纪律（见哲学注入清单）。不擅自创建/修改外部系统（GitHub 等）内容
- **文档体系内追踪**：变更记录在 docs/ 内维护（对应主题文档的变更节 / 独立 changelog），AGENTS 入口指到对应文档

**Q2 git 提交规范**（提交信息格式是项目工程的一部分，每个项目可能不同，用户选定后写入；**推荐语义前缀 + 简洁事实化风格**）：

- **Conventional Commits**：语义前缀（`feat:`/`fix:`/`docs:`/`chore:`/`refactor:`/`test:`/`perf:`/`ci:`）+ 可选 scope + 祈使句 subject + 可选 body；footer 记录 BREAKING CHANGE/issue 引用；配套 semantic-release/commitlint/自动 changelog 生态
- **语义前缀 + 简洁事实化风格**（推荐）：**强制语义前缀**（Conventional Commits 形态）；单 commit + 单行 header + 简短多行 body；附加规则：禁 em dash、避免营销词（comprehensive/utilize/streamline/leverage）、描述简洁事实化；提交生成器自动套用
- **Git 官方 50/72 风格**：无类型前缀；subject ≤50 字符、首字母大写、句末无句号、祈使语气 + 空行 + body 72 字符换行（git-commit 文档与社区共识）
- **Gitmoji**：emoji 类型前缀（✨ feat/🐛 fix/📝 docs 等），开源与个人项目流行，较不正式
- **沿用项目历史提交风格**：参考仓库现有提交格式与语言（无历史时从其他选项中选择）

**提交主动权**（谁发起提交，个人/团队偏好，**推荐限制**）：

- **限制**（推荐）：提交由用户主动发起。agent 完成实现后汇报等待用户提交（本仓库实践：提交即审查关口）
- **不限制**：agent 自由决定提交。社区主流（matt implement 明确 agent 提交）

确认后把定案写入 AGENTS.md。§1 硬规则只写提交主动权（谁发起）；格式定案写入项目提交规范（AGENTS.md 提交纪律）；提交信息写作方法（对照历史提交 diff，不按会话写）由提交 skill（h-commit）引导；agent 自行发起提交时硬规则引导使用提交 skill

**Q3 决策与理由存放处**（决策与理由全项目**统一存放一处**；**默认不建（见机制职责总览）**）：

- **无**（推荐）：默认不建。决策留在 spec 与代码注释
- **backlog**：决策记录在外部追踪系统（与 Q1 定案机制一致，如 backlog CLI/GitHub Issues）
- **docs/adr/**：文档体系内 ADR 目录，顺序编号 `0001-slug.md`，仅当"难逆转 + 无上下文会困惑 + 真实权衡"三条件触发时写（格式见 `references/ADR-FORMAT.md`）
- **主题文档"关键决策与理由"节**：不需要独立 ADR 体系，决策承载在 docs 主题文档的决策节

确认后把定案写入 AGENTS.md/architecture.md 的决策记录形态（定案"无"则不写）。**有定案时：定案形态是决策与理由的唯一存放处：主题文档/spec 不重复记录，需要时引用**。定案 docs/adr/（或主题文档决策节）后：**列出拟记录决策清单**（三条件判断的候选），**用户确认/修正后写入**。每份 ADR 记录用户确认过的决策（默认无，用户主动要求记录时才走此流程）。

**架构声明（无需问询；懒建）**：已有项目，架构是现状事实，agent 调研提取（分层/依赖方向）+ 审查判断（是否符合哲学原则、依赖方向是否健康），写入 `architecture.md` 开头声明；发现架构问题（依赖倒挂/分层混乱）在验收时指出，由用户决定是否调整。**新项目/无代码仓库，需求未定，不产出架构声明**；需求确定后（h-planning 规划）探讨架构、产出。

### 第三步：写作

**AGENTS.md（入口，只放"必须遵守"和"导航"）**：

```
- 顶部声明：本文件是入口上下文；术语权威是 docs/CONTEXT.md；历史方案勿当作当前架构
- 工具链节（放前部）：调研确定并用户确认后的项目工具链（包管理器/运行器/测试框架/构建工具/格式化），命令执行遵循该工具链规范
- 命令节：**项目自定义命令**（`uv run manage`、`./manage.sh`、自定义 scripts、CI 钩子），记录用途与用法
- §1 硬性规则：<CRITICAL> 块，5-20 条。来源 = engineering-philosophy + 项目踩坑史 + 依赖方向 + 提交主动权（Q2 定案；格式定案为项目提交规范；写作方法见提交 skill）。
  每条一句，可执行（例："禁止裸 dict 跨边界；禁止 hasattr 类型探测；yield 不能放在 with lock 内"）
- **完整规范（按需深读）**：通用工程哲学完整版（`<h-agent-docs skill 路径>/references/engineering-philosophy.md`，agent 环境可读时）+ 对应语言 craft（`<craft 路径>`），需要细节/理由时深读
- §2 文档导航（触发-必读表）：<CRITICAL> 强制 + 表格
  | 任务类型 | 必读文档 |
  原则：按"改什么"映射"读什么"，覆盖所有高频改动面；**含"改机制/重构 → 对应 topics/<主题>.md"**（主题文档持续维护，改机制必须同轮更新）
- §3 项目速览：包结构一行图 + 术语易混点（3-5 条最易错概念对）+ 关键机制摘要（每条指到对应 docs）
- §4 文档维护机制：同轮变更（改代码必须同轮更新文档，列为交付缺陷）+ 锚点用符号不用行号 + 变更记录按 Q1 定案机制登记（**默认无**，见 §5）
- §5 变更记录：按 Q1 定案形态生成（**默认"无"**，只呈现选定的机制，不列未选选项）；编写 AGENTS.md 时具体化到执行方式（如 backlog 项目写"统一走 backlog CLI、每个请求先跑 `backlog instructions overview`"）
```

**docs/（规格文档）**：每类文档的模板/职责/边界见 `references/DOCS-FORMAT.md`；不复述代码、按需生成。

**docs/CONTEXT.md（术语权威，纯词汇表）**：
格式见 `references/CONTEXT-FORMAT.md`：一句话定义（IS 非 DOES）+ _Avoid_ + 分组 + Relationships（基数）+ Example dialogue + Flagged ambiguities。

### 第四步：验证

- 模块导航索引的文件/符号 grep 存在（抽查 5 个）
- 触发-必读表引用的文件全部存在
- 术语表覆盖 scout 发现的领域专有词，混用词有裁决
- AGENTS.md 2 分钟内可读完（入口保持薄）
- 变更记录按 Q1 定案验证（定案"无"则无条目，跳过）

### 第五步：等待用户验收（验收原则）

- 生成/重写产物由用户检查（是否符合预期、与代码是否符实）；**验收通过才算完成**
- **硬规则核对**：生成 AGENTS.md 时标注从调研提取的踩坑/约束条目，验收时提示用户逐条核对（区分"项目约定"与"调研提取"）
- 不通过（方向变化/不满意的结构/术语裁决）→ 回到对应步骤（结构/写作/术语）迭代

## 维护模式（审查+修复一体）

触发：文档漂移/过时/升级后按新规范重构（用户说"完全重写"时全量重构）。

**变更类型 → 文档映射**：

| 变更类型                                                       | 更新目标                                                                       |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 新增/重命名/删除模块                                           | `AGENTS.md` §2 导航 + `architecture.md` 模块→文件索引                          |
| 新增/改动领域概念或术语                                        | `docs/CONTEXT.md`（术语权威，见 references/CONTEXT-FORMAT.md）                 |
| 用户提出的项目级约束（禁令/规范/要求，判断值得沉淀为硬规则的） | `AGENTS.md` §1 硬规则（<CRITICAL> 块）+ 对应 docs 坑节（沉淀时告知用户已记录） |
| 新增踩坑/调试经验                                              | 对应 docs 的"坑/已知行为"节                                                    |
| 机制/结构变更（重构/新增机制/抽象变化）                        | `docs/topics/<主题>.md`（机制详解，持续维护）                                  |

**不复述代码**：字段表/接口清单/信号清单等"代码即事实"的内容不写进文档；文档只承载代码表达不了的（意图/坑/术语/决策/导航/硬规则）。

**维护流程**：

1. **识别变更**：读 diff/变更描述（无 git 的项目从会话上下文/文件对比识别），按上表映射到目标文档；**对照 `references/DOCS-FORMAT.md` 检查目标文档结构**；偏离规范（旧结构/旧切分，如按层建的 backend.md/frontend.md）→ **按模板删除重写**
2. **更新意图/坑/术语/导航**：改对应 docs 的意图/坑/术语/导航索引，**锚点用"文件:符号名"**
3. **更新已知行为**：新遗留问题如实写入"已知行为/坑"节
4. **登记/更新追踪**：按项目指定的追踪机制登记或更新进展（机制见项目 AGENTS §4/§5；默认不建，见机制职责总览）；**登记/更新动作遵循外部动作纪律（见哲学注入清单）**；**不标记完成**（完成属验收后）；**生产环境敏感操作不登记追踪**（清理生产数据/生产配置变更/凭据处理等，涉及本机/实际生产环境的信息不进追踪系统）；发现文档与实际代码不符时先修文档再继续
5. **验证**：变更涉及的关键符号 grep 存在；触发表引用的文件路径有效
6. **验收后收尾**：用户验收通过后，按项目追踪机制检查验收标准并收尾（如标记完成，**遵循外部动作纪律**）；验收不通过 → 回到对应步骤迭代

## 文档体系质量硬性要求

1. 触发-必读表必须用 `<CRITICAL>` 强制（不是"建议阅读"）
2. 文档维护写进硬规则：**任何代码变更同轮更新对应文档；文档与代码冲突以实现为准并修正文档**（"代码口头改了、文档没变"= 交付缺陷）
3. 锚点一律"文件:符号名"（行号会过时）
4. 变更记录判据：**形成行为契约的才记**。改变可观察行为/接口/持久化格式/领域语义（他人会依赖、未来读者可能困惑或误用）的变更；纯内部实现（局部重构、typo、重命名局部变量、行为不变的重构）不记。一次性实验不记
5. 规格文档必须含"已知行为"节；调研发现的遗留问题如实写入
6. 可选 ADR（惯例 docs/adr/，位置以导航为准）：**默认不建（Q3 定案）**；采用时仅当"难逆转 + 无上下文会困惑 + 真实权衡"三条件全满足（格式见 `references/ADR-FORMAT.md`，内置自包含）

## 哲学注入清单（生成 AGENTS.md 硬规则时逐条对照）

从 `references/engineering-philosophy.md` 取（完整内容见该文件，此处只列注入项）：

- 类型驱动（枚举/值对象/窄化 accessor/不用 dict 实现数据类型；数据模型用类型化封装）
- 职责分层与封装（概念职责按意图划分、架构分层按依赖分、最小 API/信息隐藏；含 DDD 依赖方向）
- 契约式失败（缺失=违约快速失败，禁止防御性 fallback）
- Explicit > Magic（typed events/禁 magic string/禁 any）
- 封装过程噪声（>2 步操作封装命名函数）
- 注释纪律（注释是最后手段：先重构让注释不必要；只写代码表达不了的）
- 命名即文档与抽象时机（好函数名 > 注释；复用抽象写两次第三次，Rule of Three）
- RAII/资源作用域绑定
- 问题找根因
- Git 提交纪律（提交主动权按 Q2 定案；格式定案入项目提交规范；提交信息写作方法由提交 skill 引导）
