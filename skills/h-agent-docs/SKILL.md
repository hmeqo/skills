# agent-docs — 文档体系生成和管理

为任意项目生成**分层式 agent 文档体系**（入口 AGENTS.md + 规格 docs/，含 specs/ 设计意图；术语表按需 docs/CONTEXT.md），并自动注入工程哲学（代码原则、DDD、契约式失败、各语言规范）。生成出的文档防幻觉、防过时、与代码同轮演进。

**哲学注入**：所有生成内容默认遵循 `references/engineering-philosophy.md`（跨语言原则）与对应语言 `references/*-craft.md`。生成时把这些规范作为 AGENTS.md"硬规则"的默认素材来源。

**验收原则（贯穿所有流程）**：任何流程产物（文档体系/变更记录/重构）以**用户验收通过为完成标志**；验收不通过（不符合预期/方向变化）→ 回到对应步骤迭代（修正任务/追加进展），直到验收通过。任务追踪状态由项目自身的追踪机制（AGENTS §5 定案，如 backlog/GitHub）管理，本 skill 不越界。

## 调用方式

| 触发                           | 行为                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent-docs [<项目>]`（默认）  | 为当前/指定项目生成完整文档体系（AGENTS.md + docs/，含 specs/）                                                                                                                                                                                                                                                                                                                                         |
| `agent-docs rewrite`           | 重写现有文档体系（保留有效内容，重组结构）                                                                                                                                                                                                                                                                                                                                                              |
| `agent-docs add <模块>`        | 为已有体系追加某模块的规格文档（按本 skill 格式）                                                                                                                                                                                                                                                                                                                                                       |
| `agent-docs maintain [<变更>]` | 面对代码变更或**文档漂移**（文档与实现不一致），按维护流程同步更新；无参数时从会话上下文识别本次变更；漂移方向判定与是否值得修由用户决策（文档与实现冲突以实现为准）                                                                                                                                                                                                                                    |
| `agent-docs audit`             | skill 升级后的文档体系一致性审查（**纯文档侧**）：对照本 skill 最新设计规范（哲学注入清单/结构模板/输出清单结构）——已生成项目是否**缺漏（新增机制未生成）或与最新结构不一致**（结构/位置/命名变动未同步）+ 全部问询项 Q1-Q4 定案状态；只读输出差距清单，不自动改，修复按用户决策（未定案问询项用 ask 工具让用户重新决策）；**修复落地后按项目 Q1 定案的追踪机制登记**（见维护流程 4a，验收后收尾见 4b） |

## 维护模式（maintain）

生成后的文档体系由项目 AGENTS.md 的 <CRITICAL> 硬规则持续强制（同轮变更）。当显式调用 `maintain [<变更>]` 或改动涉及文档时，按以下流程执行（无参数时从会话上下文识别本次变更——如刚完成的 incremental-dev/debug 流程）：

### 变更类型 → 文档映射

| 变更类型                                                             | 更新目标                                                                          |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 新增/重命名/删除模块、类、函数                                       | `docs/architecture.md`（模块清单/接口清单）+ 对应模块文档                         |
| 改配置字段/默认值/参数                                               | 对应 docs 的字段表（如 pipeline.md §1）                                           |
| 改缓存键/签名/枚举值                                                 | 缓存键节 + 变更记录（枚举变必须同步缓存键）                                       |
| 加/改信号、事件                                                      | 信号清单（architecture.md 或对应文档）                                            |
| 新增/改动领域概念或术语                                              | `docs/CONTEXT.md`（术语权威，见 references/CONTEXT-FORMAT.md）                    |
| 改 UI 布局/组件/对话框                                               | `docs/ui.md`                                                                      |
| 改持久化格式                                                         | `docs/persistence.md`                                                             |
| 新增踩坑/调试经验                                                    | 对应 docs 的"坑/已知行为"节                                                       |
| 用户提出的项目级约束（禁令/规范/要求）——agent 判断值得沉淀为硬规则的 | `AGENTS.md` §1 硬规则（<CRITICAL> 块）+ 对应 docs 坑节（沉淀时告知用户已记录）    |
| 设计意图/需求/边界/验收标准变更                                      | spec 对应概念文档（按 AGENTS.md §2 导航定位，格式见 `references/SPEC-FORMAT.md`） |

### 维护流程

1. **识别变更**：读 diff/变更描述（无 git 的项目从会话上下文/文件对比识别），按上表映射到目标文档
2. **更新事实**：改对应字段表/接口清单/信号清单/术语，**锚点用"文件:符号名"不用行号**
3. **更新已知行为**：新遗留问题如实写入"已知行为/坑"节，不美化
4. **登记/更新追踪（4a）**：按项目 Q1 定案的追踪机制登记或更新进展（机制见项目 AGENTS §4/§5；集成 backlog 的项目先跑 `backlog instructions overview`）——**不标记完成**（完成属验收后，见验收原则）；**生产环境敏感操作不登记追踪**（清理生产数据/生产配置变更/凭据处理等——涉及本机/实际生产环境的信息不进追踪系统）；发现文档与实际代码不符时先修文档再继续
5. **验证**：变更涉及的关键符号 grep 存在；触发表引用的文件路径有效
6. **验收后收尾（4b，由验收循环触发）**：用户验收通过后，按项目追踪机制检查验收标准并收尾（如标记完成）；验收不通过 → 回到对应步骤迭代

### 与被动机制的配合

- **被动**：项目 AGENTS.md 硬规则"同轮变更"每次会话自动加载——agent 改代码时被强制同步
- **主动**：`maintain` 提供显式流程（类型映射 + 更新步骤）——需要时唤起
- 两者一致：都要求"文档与代码冲突以实现为准并修正文档"

## 生成流程

### 第一步：调研先行

用 scout 子代理并行分区只读调研，每区输出结构化规格要点：

- 分区建议：核心领域模型 / 基础设施与外部系统 / UI 全貌 / 算法与特殊子系统；非代码项目（纯文档/配置/技能集合）按模块或主题分区（如按 skill、按 references）
- **版本控制检查**：发现项目无 git（未初始化）或环境无 git（git 命令不可用）时提醒用户现场决策——初始化（`git init` + 按 Q3 定案提交约定）还是跳过 git 相关配置（不注入 git 纪律、Q3 不问）；有 git 则跳过此检查
- 每个 scout 必须输出：**完整类/字段/接口清单**（非摘要）、关键决策与理由、依赖方向、坑与遗留问题
- 汇总后标出需用户定案的模糊点（推测标 `[INFERENCE]`），用 grill 方式向用户确认

### 第二步：定结构（先问用户）

**问询方式：用 ask 工具（选择形式，标推荐）让用户拍板——做选择题比打字对用户更轻松；复杂场景文字说明 + 选项结合**。

**Q1 变更记录载体**（决定 AGENTS.md §4/§5 的维护机制形态——**维护者始终是 agent**（同轮变更纪律强制追加），载体由用户选，**必须问**，按选定机制执行）：

- **A. 文档体系内追踪**：变更记录在 docs/ 内维护（对应模块文档的变更节 / 独立 changelog），AGENTS 入口指到对应文档
- **B. 用户指定外部追踪**：用户选定外部机制（backlog CLI / GitHub Issues / 其他），记录本体在外部系统；AGENTS 生成**追踪工作流说明**（该机制如何参与变更流程——登记/更新进展/验收后收尾的具体步骤）
- **C. 无变更记录**：一次性实验/纯工具仓库不需要维护机制——AGENTS §5 省略或标注"无"（文档体系质量硬性要求：形成行为契约的才记）

**Q2 架构选型**（决定 architecture.md 的分层形态——架构是用户技术选型，**必须问**——列出架构选项，**推荐随项目规模**；非业务项目（纯文档/工具/脚本集合）无业务架构，架构即文档组织形态，选 B 或 C）：

- **A. DDD 分层**（domain → application → infrastructure → ui——业务复杂度高/长期演进项目时推荐）
- **B. 简单分层**（core/services/adapters 或按模块平铺——小项目/工具类时推荐）
- **C. 基于项目实际推荐的架构**（调研项目规模/复杂度/技术栈后给出认为合适的量身架构等）

确认后把选型写入 `architecture.md` 开头声明（**纯决策内容**，如"架构选型：DDD 分层"）

**Q3 git 提交规范**（提交信息格式是项目工程的一部分，每个项目可能不同——**必须问**，不默认）：

- **A. Conventional Commits**：语义前缀（`feat:`/`fix:`/`docs:`/`chore:`/`refactor:`/`test:`/`perf:`/`ci:`）+ 可选 scope + 祈使句 subject + 可选 body；footer 记录 BREAKING CHANGE/issue 引用；配套 semantic-release/commitlint/自动 changelog 生态
- **B. opencode 内置风格**：**同样强制语义前缀**（Conventional Commits 形态）——单 commit + 单行 header + 简短多行 body；附加 opencode 规则：禁 em dash、避免营销词（comprehensive/utilize/streamline/leverage）、描述简洁事实化；`/commit` 与提交生成器自动套用
- **C. Git 官方 50/72 风格**：无类型前缀——subject ≤50 字符、首字母大写、句末无句号、祈使语气 + 空行 + body 72 字符换行（git-commit 文档与社区共识）
- **D. Gitmoji**：emoji 类型前缀（✨ feat/🐛 fix/📝 docs 等），开源与个人项目流行，较不正式
- **E. 沿用项目历史提交风格**：参考仓库现有提交格式与语言（无历史时回 A-D）

确认后把定案写入 AGENTS.md 提交纪律条目（含通用行为：提交描述对照上次提交的 diff 而非本次会话）

**Q4 决策与理由存放处**（决策与理由全项目**统一存放一处**——**必须问**，不默认；**推荐 B，小项目可降级 C**）：

- **A. backlog**：决策记录在外部追踪系统（与 Q1 定案机制一致，如 backlog CLI/GitHub Issues）
- **B. docs/adr/**（推荐）：文档体系内 ADR 目录，顺序编号 `0001-slug.md`，仅当"难逆转 + 无上下文会困惑 + 真实权衡"三条件触发时写（格式见 `references/ADR-FORMAT.md`）
- **C. 模块文档"关键决策与理由"节**：不需要独立 ADR 体系，决策承载在 docs 模块文档的决策节

确认后把定案写入 AGENTS.md/architecture.md 的决策记录形态——**定案形态是决策与理由的唯一存放处：模块文档/spec 不重复记录，需要时引用**。定案 docs/adr/（或模块决策节）后：**列出拟记录决策清单**（三条件判断的候选），**用户确认/修正后写入**——每份 ADR 记录用户确认过的决策。

### 第三步：写作（B 模式模板）

**AGENTS.md（入口，100-150 行，只放"必须遵守"和"导航"）**：

```
- 顶部声明：本文件是入口上下文；术语权威是 docs/CONTEXT.md；历史方案勿当作当前架构
- §1 硬性规则：<CRITICAL> 块，5-20 条。来源 = engineering-philosophy + 项目踩坑史 + 依赖方向。
  每条一句，可执行（例："禁止裸 dict 跨边界；禁止 hasattr 类型探测；yield 不能放在 with lock 内"）
- §2 文档导航（触发-必读表）：<CRITICAL> 强制 + 表格
  | 任务类型 | 必读文档 |
  原则：按"改什么"映射"读什么"，覆盖所有高频改动面
- §3 项目速览：包结构一行图 + 术语易混点（3-5 条最易错概念对）+ 关键机制摘要（每条指到对应 docs）
- §4 文档维护机制：同轮变更（改代码必须同轮更新文档，列为交付缺陷）+ 锚点用符号不用行号 + 变更记录按 Q1 定案机制登记（见 §5）
- §5 变更记录：按 Q1 定案形态生成（只呈现选定的机制，不列未选选项）；编写 AGENTS.md 时具体化到执行方式（如 backlog 项目写"统一走 backlog CLI、每个请求先跑 `backlog instructions overview`"）
```

**docs/（规格文档，每份 100-400 行，事实库而非摘要）**：
按项目模块切分，每份覆盖：职责 + 关键符号（文件:符号名，不用行号）+ 完整字段表/接口清单/信号清单 + 关键决策与理由（按 Q4 定案形态）+ 坑/易错点 + 已知行为/遗留口径（不一致默认值、死代码、未接线 UI 如实标注）。

**docs/CONTEXT.md（术语权威，纯词汇表）**：
格式见 `references/CONTEXT-FORMAT.md`——一句话定义（IS 非 DOES）+ _Avoid_ + 分组 + Relationships（基数）+ Example dialogue + Flagged ambiguities。

### 第四步：验证

- 所有 scout 输出的字段/接口/信号全部落盘（抽查 5 个符号 grep 存在）
- 触发-必读表引用的文件全部存在
- 术语表覆盖 scout 发现的领域专有词，混用词有裁决
- AGENTS.md 2 分钟内可读完（入口保持薄）
- 变更记录已含本次文档建立的条目

### 第五步：等待用户验收（验收原则）

- 生成/重写产物由用户检查（是否符合预期、与代码是否符实）——**验收通过才算完成**
- **硬规则核对**：生成 AGENTS.md 时标注从调研提取的踩坑/约束条目，验收时提示用户逐条核对（区分"项目约定"与"调研提取"）
- 不通过（方向变化/不满意的结构/术语裁决）→ 回到对应步骤（结构/写作/术语）迭代

## 文档体系质量硬性要求

1. 触发-必读表必须用 `<CRITICAL>` 强制（不是"建议阅读"）
2. 文档维护写进硬规则：**任何代码变更同轮更新对应文档；文档与代码冲突以实现为准并修正文档**（"代码口头改了、文档没变"= 交付缺陷）
3. 锚点一律"文件:符号名"（行号会过时）
4. 一次性实验不记变更记录；形成行为契约的才记
5. 规格文档必须含"已知行为"节——调研发现的遗留问题如实写入
6. 可选 ADR（惯例 docs/adr/，位置以导航为准）：按 Q4 定案；采用时仅当"难逆转 + 无上下文会困惑 + 真实权衡"三条件全满足（格式见 `references/ADR-FORMAT.md`，内置自包含）

## 哲学注入清单（生成 AGENTS.md 硬规则时逐条对照）

从 `references/engineering-philosophy.md` 取：

- 类型驱动（枚举/值对象/窄化 accessor/无裸 dict）
- 职责分层与封装（概念职责按意图划分、架构分层按依赖分、职责归属不明确时 ask 用户、最小 API/信息隐藏；含 DDD 依赖方向）
- 契约式失败（缺失=违约快速失败，禁止防御性 fallback）
- Explicit > Magic（typed events/禁 magic string/禁 any）
- 封装过程噪声（>2 步操作封装命名函数）
- RAII/资源作用域绑定
- 治本不治标（问题找根因）
- Git 提交纪律（提交由用户发起；对照 diff 而非会话；格式/前缀/语言按 Q3 定案注入，不默认 Conventional Commits）

从对应语言 `references/*-craft.md` 取该项目的语言规范。

## 输出清单

```
<项目>/
├── AGENTS.md             # 入口（硬规则 + 导航 + 维护 + 变更记录）
├── docs/
│   ├── CONTEXT.md        # 术语权威（按需生成，有业务领域术语时）
│   ├── specs/            # 设计意图与需求 spec（惯例位置，按概念一份，格式见 references/SPEC-FORMAT.md——incremental-dev 规划共识时产出，位置以导航为准）
│   ├── architecture.md   # 跨包架构 + DDD + 信号/接口清单
│   ├── pipeline.md       # 核心管线/领域模型（按项目领域命名）
│   ├── ui.md             # UI 布局（如适用）
│   ├── persistence.md    # 持久化格式（项目有自定义持久化格式时生成）
│   └── ...               # 按模块扩展
└── 变更记录条目
```
