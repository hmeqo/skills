# ADR Format（架构决策记录格式）

> 参考 mattpocock/skills 的 domain-modeling ADR-FORMAT，内置自包含——不依赖外部 skill。

ADRs 位于 `docs/adr/`（惯例位置——实际以 AGENTS.md §2 导航为准），顺序编号：`0001-slug.md`、`0002-slug.md`……首次需要时懒创建目录。

## 模板

```md
# {决策短标题}

{1-3 句：背景是什么、决定了什么、为什么。}
```

就这些——ADR 可以是一段话。价值在记录"做了决策、为什么"，不在填格式。

## 可选节（仅当有真实价值时加）

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——决策会被 revisit 时有用
- **Considered Options**——被拒绝的替代值得记住时
- **Consequences**——非显然的下游影响需要指出时

## 编号

扫 `docs/adr/` 最高编号 +1。

## 何时写 ADR（三条件全满足）

1. **难逆转**——事后改主意成本高
2. **无上下文会困惑**——未来读者看到代码会问"为什么这样做"
3. **真实权衡的结果**——有真实替代方案，因具体理由选了其一

轻松可逆转 / 不令人困惑 / 没有真实替代 → 跳过。

### 什么算 ADR

- **架构形态**：monorepo、事件源写模型等
- **上下文间集成模式**：领域事件 vs 同步 HTTP
- **带 lock-in 的技术选择**：数据库/消息总线/认证商/部署目标——不是每个库，是换掉要花一个季度的
- **边界与范围决策**："数据归 X 上下文，其他只引用 ID"——显式的不做和做了同样有价值
- **对显而易见路径的刻意偏离**：手动 SQL 而非 ORM 因为 X——防止下一个工程师"修掉"有意的设计
- **代码里不可见的约束**：合规限制、响应时间契约
- **被拒绝的替代（拒绝理由非显然时）**：考虑过 GraphQL 选了 REST 的微妙理由——否则半年后又有人提议 GraphQL
