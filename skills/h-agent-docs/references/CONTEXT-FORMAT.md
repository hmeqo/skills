# CONTEXT.md 格式 — 领域术语表规范

> agent-docs 生成 docs/CONTEXT.md 时遵循的格式。CONTEXT.md 是项目的**领域语言权威**：只定义"词是什么"，不含实现细节。

## 结构

```markdown
# <上下文名>

<一两句话：这个上下文是什么、为什么存在>

## Language

**<术语>**:
<一句话定义（是 IS 不是 DOES）>
_Avoid_: <同义词、易混词>

## Relationships

- 一个 **A** 产生若干 **B**
- **B** 属于恰好一个 **A**

## Example dialogue

> **Dev:** "..."
> **Domain expert:** "..."（展示术语边界）

## Flagged ambiguities

- "X" 曾被用来指 Y 和 Z，已解决：二者是不同概念
```

## 规则

- **Be opinionated**：一词多义时选最佳词，其余列为 `_Avoid_`
- **Flag conflicts explicitly**：混用词写入 Flagged ambiguities 并给出裁决
- **定义要紧**：一句话，定义"是什么"不是"做什么"
- **Relationships 用加粗术语名**，表达基数（一个/若干/恰好一个）
- **只收项目特有概念**：通用编程概念（超时/错误类型/工具函数）不收，问自己"这是本上下文独有的概念吗？"
- **自然聚类时分组**（子标题），单一领域则平铺
- **Example dialogue**：开发与领域专家的对话，展示术语如何自然交互、澄清相关概念边界

## 分组示例（多领域项目，分组名按项目实际领域，以下仅为示意）

```
### 核心域        # 领域模型核心
### 集成域        # 外部系统/硬件
### 界面域        # UI/交互
### 持久化域      # 存储格式
```

## 多上下文项目

- 单上下文：`docs/CONTEXT.md`（惯例位置，实际以 AGENTS.md §2 导航为准）
- 多上下文：`docs/CONTEXT-MAP.md` 列出各上下文位置与关系；各上下文内放自己的 CONTEXT.md

## 维护纪律

- 术语解决即写入（不攒批）
- 新增领域概念时同步更新（agent 改代码同轮变更）
- 与实现冲突时**向用户呈现矛盾并判定以谁为准**：术语表确为意图（驱动命名）则改代码；代码确为意图则修正术语表
