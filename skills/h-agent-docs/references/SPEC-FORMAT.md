# SPEC Format（设计意图与需求规格格式）

> 记录"意图、需求、为什么这么做"的规格文档——规划共识的持久化载体，对齐 mattpocock to-spec 思想，轻量落地于文档体系（不依赖 issue tracker）。

## 位置与命名

- 目录：`docs/specs/`（惯例位置——实际以 AGENTS.md §2 导航为准；首次需要时创建）
- 命名：按**概念**一份，小写连字符：`architecture.md`（架构理念）、`<套件名>.md`（功能套件）、`<流程名>.md`（流程）、`<功能名>.md`（功能）
- 划分判据：**独立演进单元**——会独立变化/独立验收/独立引用的概念一份；永远一起变则合并；概念粒度对齐 CONTEXT.md 术语

## 模板

```md
# <概念> 设计意图与需求

## 意图

{为什么做 / 为什么这样设计——设计理念，1-3 句}

## 需求

{要什么：概述 + 可选编号清单（拷问确认点逐条落位；功能类可写"作为 <角色>，我希望 <能力>，以便 <收益>"，架构/流程类一句话需求）}

## 方案概述

{怎么解决：高层设计意图——详细实现走模块文档、决策理由走 Q4 存放处，三者分界明确}

## 边界（Out of Scope）

{明确不做的——scope 而非 sharpness 决定}

## 验收标准

{随规划产出，实现后照单验收；每个决策点对应验收表述}
```

价值在记录"意图与为什么"，不在填格式。可选节（有真实价值时加）：需求清单（概述不够时）、测试决策。（决策与理由按 Q4 定案形态统一存放，spec 不承载——需要时引用。）

## 何时写

- 规划共识达成时（h-incremental-dev 产出）——需求、为什么、边界不活在对话里（易失）
- 实现与验收对照 spec

## 如何维护

- **更新时机**：需求/意图/边界变化时（回环/用户提出）——不是每次代码变更（代码变更更新 docs 事实库，spec 是意图层）
- **实现偏离 spec**：回环纪律判断——意图变了 → 改 spec；实现错了 → 改实现
- **分段执行**：spec 存档后实现可在后续会话进行（新会话读 spec 继续，无需重新规划）
- **补建 spec（旧项目，audit 发现缺失后）**：枚举现有功能（模块文档/代码清单）→ 逆向重建全部 spec 草案（标 `[INFERENCE]`）→ **聚合核对**（一次呈现所有草案摘要、编号 + 推荐，用户整体过一遍指出问题/补全）→ 浮现的新问题（跨功能关联/漏项）按依赖组织追问 → 用户确认后定稿

## 防丢失

- AGENTS.md §2 文档导航指向 spec 文档位置——任何会话加载入口即可见，意图/为什么不随会话消失
