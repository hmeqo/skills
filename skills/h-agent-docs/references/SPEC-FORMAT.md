# SPEC Format（设计意图与需求规格）

> 记录"问题、解决方案、需求、设计决策"的规格内容，规划共识的持久化载体，对齐 mattpocock to-spec：承载于**spec 文档（docs/specs/，文档形态）或 GitHub issue（追踪系统形态）**，按项目选择（Q1 定案机制：**默认不建追踪**，用户选择外部承载才用 issue；非 backlog，backlog 只承载普通任务）。

## 位置与组织

- 承载：spec 文档（`docs/specs/<机制>.md`，文档形态）或 GitHub issue（issue 形态，社区称 ticket），两者同一设计意图的两种承载
- 组织：按**概念**一份（文档）或一个任务（issue），**独立演进单元**（独立变化/独立验收/独立引用）一份；永远一起变则合并；概念粒度对齐 CONTEXT.md 术语
- 命名：小写连字符（如 `file-transfer`、`cron-schedule`）

## 模板（设计意图正文，docs/specs 文档或 issue 正文共用）

```md
# <概念> 设计意图与需求

## 问题陈述

{用户面对的问题，从用户视角写，为什么做}

## 解决方案

{怎么解决，从用户视角写}

## 需求（User Stories）

{需求清单，自然语言逐条，覆盖该功能所有方面，拷问确认点逐条落位}

## 设计决策

{怎么解决（技术层）：结构/架构/模块接口/schema/API 契约/特定交互/UI 布局/开发者的技术澄清}

## 测试决策（按需）

{测哪些模块 + 好测试标准 + 测试 prior art}

## 边界（Out of Scope）

{明确不做的}

## 验收标准

{随规划产出，实现后照单验收；每个决策点对应验收表述}

## 其它说明（按需）

{无法归入其他节的杂项}
```

**写法说明**：
- **spec 是任务触发/新 agent 上下文的唯一来源，决策尽量详细不省略**
- 文件路径/代码片段不进 spec（过时快：代码即事实，grep 即得）
- 设计决策含**开发者的技术澄清**（讨论中澄清的技术约束，后续 agent 最需要的上下文）
- 规划确认的 ASCII 草图可内联 + 注明来源；原型产出的精确决策片段（schema/type shape/state machine）可内联，修剪到决策核心（非工作 demo）
- 决策理由走 adr（Q3 定案）；测试 prior art = 代码库相似测试

价值在记录"问题与解决方案"与**完整设计决策**，不在填格式。（Q3 定案**默认不建**，有定案存放处时决策与理由统一存放、spec 不重复；无存放处时决策留在 spec 与代码注释。）

## 何时写

- **按需**：形成行为契约/复杂/跨会话的变更（h-planning 规划共识达成时），简单增量对话确认即可，不强制产出
- 实现与验收对照设计意图的验收标准

## 如何维护

- **更新时机**：需求/问题/边界变化时（回环/用户提出），不是每次代码变更
- **实现偏离 spec**：回环纪律判断：意图变了 → 更新设计意图（文档/issue）；实现错了 → 改实现
- **实现完成后**：docs/specs 承载 → 归档；issue 承载 → 关闭（历史保留，可追溯）
- **分段执行**：设计意图存档后实现可在后续会话进行（新会话按承载位置继续，无需重新规划）
