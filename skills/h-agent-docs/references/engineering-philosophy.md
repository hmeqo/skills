# Engineering Philosophy — 跨语言工程哲学

> agent-docs 生成 AGENTS.md 硬规则时的默认规范来源。所有生成的项目文档硬规则从下表提炼，并补充该项目自己的踩坑史。

## 代码原则（工作方式）

- **关注代码结构**：执行前考虑如何配合/重构现有架构，维持可读性、可维护性、健壮性
- **调研先行**：写代码前调研最优解，检查基础/第三方库是否已有更好实现
- **概念先于实现**：任何工作（开发/调试/重构）先核对概念/抽象/设计（需求意图、领域语义、设计取舍），确认无错后才进入实现问题；bug 报告先排除设计层（"这是设计问题不是代码问题"）
- **反复强调的纪律立即固化**：用户强调多次的纪律（重要、必须遵守、易被遗忘）立即写进规范（哲学/硬规则/skill），规范承载，保证持续遵守
- **独立审查（subagent）**：需要 review/检查（代码/文档/一致性）时派**独立子代理**执行：独立视角（自查同视角看不出问题）+ 防上下文污染（检查内容不进入主上下文）。用户要求 review 时主动采用，无需提醒
- **技术信息查证**：外部事实与技术主张（用户陈述、方案依赖的现状、文档引用的规范）不凭记忆/猜测，联网搜索后验证时效性（发布时间/版本/维护状态/是否被新技术取代）与可靠性（官方文档 > 社区共识 > 个人文章，关键决策交叉验证），确认后采信；与用户主张不一致时以证据指出；过时/不可用信息不采信并给出替代，无法确认标 [INFERENCE]。**区分决策与事实**：用户的技术选型/品味是决策（尊重并给方案）；用户的事实性主张（含"X 是不是 Y"的假设）先核证再回应；说错以证据指出，不模糊认同
- **优雅代码优先**：优先重构优雅解决问题；无意义重复/硬编码/过度耦合都是缺陷；职责清晰分层，适当封装过程式噪声
- **如何重构**：在完整封装和类型安全基础上重构，不因简化而简化；从长远整体架构考虑概念和分层；重构可以是概念修正/拆分/重组/新代码适配
- **问题找根因**：确定根本原因，修复策略由此展开

## 注释纪律

- **注释是最后手段**：写注释前先尝试重构：好命名/提取函数/简化结构让注释不必要。需要注释常是代码表达失败的信号
- **绝不描述代码**：不解释代码做了什么（"遍历列表求和"是噪音）；读者懂代码、不懂你的意图，注释只写代码表达不了的：意图（为什么）、不变量、非显然约束、坑（一行内）
- **公共 API 文档化**：公共接口（导出函数/类/模块）的 docstring 给调用者契约（参数/返回/异常，调用者不用读实现）。格式按对应语言 craft
- **TODO 带上下文**：TODO 注释附 issue 链接/具体事件/日期（可搜索可追）。不挂无上下文的过期日期
- **注释会腐烂**：与代码矛盾时注释是错的，随代码同步更新；注释掉的代码删除（git history 有）
- **架构/行为契约说明进文档体系**（docs/ 规格 + 变更记录），不写进代码注释：大段"该怎么做/为什么这样设计"属于文档，代码注释只留代码局部的 why
- **变更性说明属于 git history**：不解释"为什么没有别的东西"（"不再使用 X""已移除 X"），git 有记录，不进代码

## 提示词与规则写作（正面优先）

- **正面为主**：能用"做什么"表达的不写"别做什么"，don't 堆砌使 agent 保守少干活（社区实测：连续 don't 无 do → 过度探索、少干活）
- **反面仅两种场景保留**：① 防 agent 默认模式（agent 会 fallback 最常见做法，如"禁止裸 dict 跨边界""禁止 hasattr 类型探测"）；② 无法正面表达（只能排除）
- 关键反面与正面规则并列使用，无显式 don't 时 agent 倾向最常见模式

## Type-Driven Design（类型驱动）

| 理念                             | 实践                                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Newtype 包裹原始类型             | 包含领域含义时包，不当使用增复杂度                                                                                                          |
| Tagged union 表达多态            | 优先；继承仅在需共享默认实现时                                                                                                              |
| 值对象优先代替裸 object/map/dict | 不用 dict 实现数据类型，数据模型用类型化值对象（dataclass/NamedTuple/BaseModel/serde struct/enum），类型安全无特例 |
| 枚举优先代替魔法值               | 变体由类型系统枚举（enum/sum type）而非文档约定；不用 magic string/number                                                                   |
| 架构逻辑优先代替断言             | 约束用类型与架构表达（所有权/RAII、可空与错误值类型、构造时校验）；断言仅当架构无法实现且类型检查器无法判断时兜底，且必须封装，不散落调用方 |

能用类型编码的约束不留到运行时。

## 职责分层与封装

职责划分有两个维度：**概念层**（因意图/需求划分，最细粒度）与**架构层**（大范围分层）。**职责归属不明确时 ask 用户使其明确**：概念边界/职责划分是用户决策（领域意图），agent 查得到现状（代码/术语表）但查不到意图。不猜、不默认。

### 概念职责划分（因意图和需求划分）

- **概念封装优先于功能封装**：模块边界按**概念**抽象划分（顶层，抽象/稳定），功能作为概念的实现内容在更底层（具体/易变）。边界先问"这是什么概念"，再落"哪些功能属于它"；按功能直接切边界（功能即模块）随实现变化频繁，概念边界变化慢（呼应"按为什么变化分模块"）
- 领域概念按**意图/需求**划分职责：每个概念的边界（管什么、不管什么）由它**服务的意图**决定，同一领域内按用途分拆（如"工件 ≠ 资产""层 ≠ 遍"，各管各的意图）
- 概念边界判据：**"这个概念的职责是什么？它在为什么意图服务？"**。两个概念服务不同意图 = 分开；同一意图的变体 = 归并
- 落地载体：术语表（docs/CONTEXT.md，惯例：每个术语 = 一个概念职责单元）+ 类型/模块边界

### 架构选型与分层（按"依赖什么"分）

**架构是技术选型（用户决策），列出可选架构与取舍，推荐 DDD**（分层/DDD/六边形/端口-适配器/事件驱动/CQRS 等按项目取舍）：

```
domain（业务规则）→ application（用例编排）→ infrastructure（外部世界）→ ui（呈现）
```

| 层             | 职责（管什么）                              | 判断依据                                                    |
| -------------- | ------------------------------------------- | ----------------------------------------------------------- |
| domain         | 业务规则/领域概念/不变量/算法               | 这段逻辑依赖外部世界吗？不依赖（纯逻辑/数据变换）= domain |
| application    | 用例编排（调领域操作 + infra 接口串成用例） | 它只是把已有能力串起来吗？是 = application                |
| infrastructure | 硬件/持久化/网络/DLL/文件                   | 它触碰外部资源吗？是 = infra，实现 domain 定义的接口      |
| ui             | 呈现与交互                                  | 它是给用户看的吗？是 = ui，承载最少业务逻辑               |

依赖方向单向向下：domain 零 IO、零框架、零 UI 依赖；application 通过 trait/接口间接调 infra；infra 实现 trait，反向依赖 domain。

判据一句话：**按"依赖什么"分层，按"为什么变化"分模块**，同层内模块按变化原因聚合（高内聚），跨层只走窄接口（低耦合）。

### 职责封装（边界与信息隐藏）

| 原则         | 实践                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------- |
| 最小公共 API | 暴露接口只含调用方需要的操作，不暴露内部状态/临时方法                                               |
| 信息隐藏     | 调用方只见契约（签名/接口），不见内部（数据结构/算法/缓存）。"调用方需要知道多少内部信息？越少越好" |
| 单一职责     | 一个模块/类一个变化理由："它为什么而变化？"回答应只有一个主语                                       |
| 窄接口跨边界 | 跨模块通信用窄接口（签名明确的函数/消息），不传内部对象                                             |

### 封装（提取 vs 抽象，时机）

- **提取命名函数（语义，可读性）**：难读/多步（>2 步）的代码**立即提取**，能提取就提取，**意图与实现分离**（读者看函数名知意图，不读实现）。复杂链式调用（`lst.map(...).filter(...).reduce(...)` 等）有具体含义就语义化封装（如"提取列表中所有字符串长度的平方的阶乘的和"，命名函数表达意图）。提取产物天然可复用（第二处出现相同意图时直接调用已有函数，不再重复提取）
- **抽象/泛化（复用设计，泛型/参数化/接口/抽象层）**：**写两次，第三次抽象**（Rule of Three）。重复出现先复制两次。重复远便宜于错误抽象（Sandi Metz：duplication is far cheaper than the wrong abstraction）。第三次共同点清晰，抽象设计才正确。真实需求出现时才抽象
- 命名即文档：好函数名 > 注释 > 反封装的内联

## Contractual Failure（契约式失败）

所有函数调用隐含"你会满足前置条件"。违反 = 合约违约，不是"给默认值悄悄继续"：

- 缺失数据 = 违约，快速失败，不静默补默认值
- 满足前置条件时，实现方必须保证后置条件/不变量，输出契约与输入契约同样强制
- 选填字段仅当外部接口明确定义默认值时用 fallback
- 不做防御性向后兼容 fallback，除非明确要求
- 核心路径零错误静默丢弃，错误必须传播

## 错误表达选型

错误用什么机制表达是先行的技术选型，确定后全项目统一：Rust `Result`（错误即值、调用方穷尽处理）、Python/TS 异常（沿调用栈传播）、C++ 异常或错误码（按项目取舍）。

- 选型统一不混用：不出现一半异常、一半返回值判断错误
- 错误带上下文：错误类型/信息说明"什么错了、为什么"，不吞异常、不丢信息（呼应 Contractual Failure）
- 跨边界用类型化错误：跨模块/跨端定义错误类型或错误码，不用裸字符串/魔法值判断错误

## Explicit > Magic（显式优于魔法）

- typed events 代替 string-based
- 枚举/常量替代 magic strings/numbers
- `any`/`dynamic` 项目级禁止
- 命名 accessor 代替 inline match/isinstance，变体分类决策集中一处

## Encapsulate Process Noise（封装过程噪声）

链式/过程式代码堆叠到难一眼看出意图时，提取命名函数：

| 层次             | 示例                                          | 封装目标                         |
| ---------------- | --------------------------------------------- | -------------------------------- |
| Collection chain | 过滤/映射/聚合链（filter/map/reduce、推导式） | 命名函数隐藏组合细节             |
| 多步骤初始化     | create+start+parse+cleanup                    | 构造函数 + RAII guard            |
| 基础设施细节     | 原始 SQL/序列化/协议字节                      | 命名函数，调用方不接触领域外概念 |
| 语言机制         | 引用计数/写时复制/锁                          | wrapper 暴露自然接口             |

**超过 2 步的过程式噪声必须封装成命名函数**。目标不是消灭链式，是给过程逻辑命名。

## 跨端类型同步

手动同步两处 = 100% 会忘。跨端（前后端分离、Rust↔TS 壳内桥接、多语言服务间）共享的类型必须由单一事实来源生成，禁止两端各自手写维护，各维护一套 = 双份注意力，必然漂移。

先做技术选型，确定同步机制并全项目统一：前后端分离 → 后端提供 OpenAPI schema 生成客户端类型；Tauri 壳内 Rust↔TS → tauri-specta 从 command 签名生成 TS 类型；多语言服务间 → Protobuf 等消息协议；后端自动生成 TS 类型由前端直接消费。

机制确定后：契约变更 → 重新生成 → 不匹配编译期暴露。生成代码标注"勿手动编辑"。

## RAII Guard Pattern

资源生命周期绑定作用域：获取即初始化、离开作用域自动释放，调用方不操心。正常返回与异常/提前退出路径同样自动释放，无需显式 cleanup，杜绝泄漏与忘记释放。

跨语言同一思想：C++ 析构函数、Rust `Drop`、Python `with`/context manager。

## Git 提交纪律

- **提交由用户主动发起**：git 提交（含 amend/合并提交）只在用户主动提出需求时执行
- **提交信息对照历史 diff 写**：commit 信息写"与已提交状态相比改了什么、为什么"，对照上次提交的 diff，不按会话/工作过程写（会话做了什么 ≠ 提交信息）

## 外部动作

- **创建/更新追踪条目与外部内容由用户主动发起或显式征得同意**：issue/PR/评论/backlog 条目/ADR/决策记录，不擅自创建/修改外部系统（GitHub 等）内容

## 隐私与信息纪律

凭据/密钥/token、个人隐私、商业机密、内网/基础设施细节、用户明确要求不记录的内容，**不写入文档体系**（AGENTS.md / docs / spec）或**追踪系统**；已有记录中发现的隐私信息移除。

**信息来源不记录**：注释/文档不标注来源。

## 沟通风格

- 代码引用格式：`file_path:line_number`
- 仅在用户明确要求时使用 emoji
- 简洁、证据导向：每句一个事实/决定/风险
