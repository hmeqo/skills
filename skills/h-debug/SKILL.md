# 调试工作流

以**项目规范与 skill 最佳实践为基底**（AGENTS.md 硬规则、engineering-philosophy、语言 craft）——诊断与修复都不偏离既有约定。

用户报告 bug/异常行为时，按**验收驱动的循环**执行——验收通过前任务保持追踪。

## 流程

**一体循环：明确预期 ↔ 诊断 ↔ 尝试修复（试探性）——交织演进，逐步确认**。根因确认、修复方案成形后，**采取修复方案前告知用户并征得同意**。

### 一体循环（搞清楚问题——预期/诊断/尝试修复互锁）

- **起步问初始预期——先输出前置内容（现象/报错/相关代码上下文）再用选择工具让用户拍板**：应该是什么行为、边界（修到什么程度/涵盖哪些场景）、与既有行为的差异（以前/其他场景什么样 vs 报告的现象）——每个点给出明确选项，标推荐项
- **复述你的理解（含推断），逐点让用户确认是否一致**（用户的描述与你的推断可能有偏差）
- **验收标准随预期产出**：预期确认时同步明确验收基准（用户测什么 = 预期行为——修复后按预期验证），验收时不事后另想
- **诊断**（先宏观后微观：先架构/逻辑链条，再代码行/参数；方式按需组合）：
  - 日志判断（现有日志/报错）
  - **自行加入输出/日志辅助判断**（临时 print/日志，定位后清理——大量/高频日志、后台/异步进程、崩溃后查证、多次运行对比时改用**日志输出文件**：写文件而非 console，文件持久可查可对比；调试日志带唯一前缀便于清理）
  - 阅读代码/静态分析——**专注逻辑链条与架构判断**（很多 bug 是架构失误的连锁）；发现是设计缺陷时明确说出"这是设计问题不是代码问题"
  - 检查与既有设计/注释/文档的冲突；git 历史定位引入点
  - 最小复现/实验——**先建 tight 复现信号**（能对目标 bug 变红的一次性命令/测试/脚本；没有能复现的信号时停下来明确告知，问用户要环境访问/工件/插桩许可，不跳进假设）；**含尝试性修改验证假设**（改参数/小改观察——试探是诊断手段：日志插桩自主进行并告知用户，逻辑改动征得同意）
  - 库/框架行为异常（参数签名、API 变化、stub 行为）→ **联网查官方文档/版本变更/已知 issue**，以权威来源为准
  - **批判性验证根因**：替代解释能解释全部现象吗（反证/排除）——结论经证据链支撑后再采信
- **预期随诊断/尝试结果修正**（发现根因后，"应该是什么"更清楚——用户描述的可能是表象而非真意）——循环直到**预期与根因都确认**
- **复现匹配用户症状**：复现/实验产生的失败模式必须与用户描述的症状一致——不是旁边恰好相似的另一个 bug（wrong bug = wrong fix）；预期核对用"你描述的现象是这样吗"这类自然询问，不用固定句式
- **可证伪假设 + 排名展示**：作出问题判断时生成 3-5 个可证伪假设（"如果 X 是原因，则改 Y 会使 bug 消失"）——无法陈述预测的假设是感觉，丢弃或锐化；**排名列表展示给用户重排/排除**（用户常知"刚部署过 #3"或已试过的假设），不默认自己的判断进入下一步；用户不在场不阻塞，按自己排名继续；是否用 ask 工具（选项形式）看实际情况——一般有 ask 用户看起来更清晰

### 实施与验收（同意后）

修复方案实施前征得用户同意：**一次性给全完整方案集 + 明确推荐**（残缺或无推荐视为未完成；**关键取舍以问题形式逐一提出**（"补丁还是重构？""修这里还是根上？"）；**批判性审视每个方案**（副作用/是否掩盖真因）；**推荐方案附决策依据摘要**（为什么选它、排除其他选项的理由——用户看清推理链）；从长远/整个项目考虑，允许架构变动）——得到同意后进入实施。

1. **创建/更新任务**：按项目追踪系统（如 backlog）创建/更新 task（无则建，有则续用）——循环迭代时追加进展（用户可追溯）
2. **实现**：按方案修复 + **同轮同步文档**（变更→文档映射按 `h-agent-docs maintain` 流程，见其维护模式）。**调试代码清理**：定位用的临时输出（print/实验性日志）在根因确认后清理；有长期诊断价值的日志保留为 debug 级（低开销）并注明用途
3. **等待验收**：实现完成后**汇报时显式列出验收点**（用户测什么、怎么确认）；任务挂起期间**在合适时机主动提醒**（新对话/用户问进度/相关话题/会话末），让用户及时验收
   - **通过** → 完成任务（检查验收标准 → 标记完成）+ 文档收尾
   - **不通过**（不符合预期 / 预期需纠正）→ 修正任务 / 追加进展 → **回到一体循环（重新明确预期）** → 循环

**多轮迭代是常态**：修复可能引出新问题（连锁/回归），新问题同样回到一体循环（重新明确预期 → 诊断 → 新方案 → 同意 → 修复）——每轮循环在任务里追加进展（用户可追溯）。
