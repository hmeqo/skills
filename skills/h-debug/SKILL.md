# 调试工作流

先建反馈回路再假设，诊断确认后经同意门再修，验收通过才算完。

## 诊断

1. **明确预期**：核对设计意图/概念（bug 可能源于设计层，明确说出"这是设计问题不是代码问题"）；明确边界；验收标准随预期产出
2. **建反馈回路**：先建 tight 复现信号（能对目标 bug 变红的一次性命令/测试/脚本）；建不起来时停下明确告知，问环境访问/插桩许可；复现必须匹配症状；失败案例最小化（bisect/二分定位）
3. **假设生成与排名**：3-5 个可证伪假设（"如果 X 是原因，则改 Y 会使 bug 消失"）；排名列表展示给用户重排/排除；批判性验证根因（替代解释能解释全部现象吗）
4. **诊断手段按需组合**：日志、插桩、读代码、查 git 历史定位引入点、查官方文档、试探性修改验证假设（日志插桩自主、逻辑改动征得同意）

**出口**：预期、根因、复现信号对齐才进同意门；任何一环未确认回到对应步骤。

## 同意门

一次性给全完整方案集 + 明确推荐；批判性审视每个方案（副作用/是否掩盖真因）；推荐附决策依据摘要；从长远/整个项目考虑，允许架构变动。**用户不在场**：诊断/调查可继续（告知），**采取修复方案必须等用户同意**。

## 实施

1. **修复**：对照哲学与 craft；同轮同步文档；**回归**（跑复现信号确认 bug 消失 + 按项目测试约定跑相关测试）；清理调试代码（有长期诊断价值的保留为 debug 级并注明用途）
2. **验收**：列出验收点 ask 用户；不通过回诊断块（重新明确预期）循环

**多轮迭代是常态**：修复引出新问题（连锁/回归）同样回诊断块。**涉及大幅改动/跨会话的调试走 `h-planning`**。
