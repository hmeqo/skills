# 规划工作流

先锚定现状再做变更规划；讨论连续推进，停下问用户只限「交互」节列出的情况。

## 锚定现状（有现状时）

读现有代码/概念/行为，明确变更基准（现状现在怎么做的、谁依赖它）。每个决策对照现状问"改变现有什么、谁受影响、是替换还是新增"。

## 需求与意图（先做）

先明确为什么做（解决什么问题/服务什么目标）；**开放确认**（用户自由表达，不做选择题）；意图优先于一切细节。边界（做什么/不做什么）。复述理解（含推断）让用户确认一致。**主动批判性挖掘**：头脑风暴发散提方向再收敛，主动发现用户没发现的点（需求盲区/技术风险/未考虑边界），有主见。

## 批判纪律

规划全程主动发现并批判性提出所有问题（需求盲区/技术风险/方案缺陷/未考虑边界/对存量代码的影响），随时提出，不等用户问。方案获用户认可后仍须自我审查；用户赞同不等于方案无缺陷，不因赞同放松批判。

## 决策树（问询）

需求/设计组织成**决策树**，每轮问整个 **frontier**（前置已决的全部决策，编号 + 推荐答案），回答后重算 frontier 再问下一轮。环境可查的事实自行查取；必然派生项不是决策不进树。设计决策对照通用工程哲学（`skill://h-agent-docs/references/engineering-philosophy.md`，规范来源）。

**方向**：按 frontier（依赖关系）推进：意图确认后从**最直接依赖意图的决策**开始（范围/边界优先：先定范围再深入细节），沿依赖逐层展开。任何节点变动沿关联传播：受影响的决策/概念跟着重审；触及根基（意图/概念层）则重审所有依赖它的决策，必要时概念层整体重构。

**层间影响**：设计发现问题回概念层修正；实现约束影响前面决策时提前确认（技术可行性/硬件/SDK 限制）；实现中的问题回环推翻设计。

**双向探讨**：双方自由提出观点、互相提出问题（批判性审视需求，自己的理解/方案也开放给用户讨论；有主见，可坚持合理立场，也愿意调整）。收敛 = frontier 清空且**方案经受住双方质疑**（用户认可理解；确认方案客观成立，直到双方都认可这套方案）。**达成共识前自问：还有没有遗漏？真的达成共识了吗？自检通过才算收敛，否则继续回环**。

## 交互

**讨论连续推进，不阶段询问**。停下问用户只在这两种情况：
- **重大决策/方向变化**：用 **ask 工具**呈现选项（选择题、标推荐）——这是给选项，不是问"要不要继续"；问前先输出前置内容（意图、UI 字符画、流程、关键思路，文字承载方案与上下文）
- **收敛确认**：方案经受住质疑、自检无遗漏后，确认双方认可

其余讨论自己走（派生项自定、方案自推），不打断用户。

## 设计确认（有 UI 时）

ASCII 草图（布局/控件/交互形态）+ 功能流程图（数据流/状态流转，mermaid 或文本）。

## 方案确认

一次性给全完整方案集 + 明确推荐：关键取舍以问题形式逐一提出；推荐附决策依据摘要（为什么选它、排除其他选项的理由）；批判性审视每个方案（副作用/是否掩盖真因）；主动寻找方案盲点（未考虑场景/被排除的替代/未检验的假设）；从整个项目/长远考虑，允许架构变动；方案依赖外部事实时联网查证（官方文档为准，验证时效性）。

## 规划演进与重审

推进到关键节点（层转换/重大决策后）回头重审已确认部分（一致性/遗漏/冲突），更新 spec 细节（已有 spec 时）；问题按回环纪律处理。规划完成时最终审一遍，确认规划无问题才达成共识；发现遗漏/冲突回环处理。

## 回环纪律

任何变动触及概念/归属/意图 → 回到需求与意图重新明确；触及设计/方案 → 回到对应项；触及现有概念（新需求改变既有语义/归属）→ 概念层重新梳理现有概念（新旧概念映射/演进）；触及存量代码（新需求改变既有行为/结构）→ 实现层提出迁移/适配方案（评估影响面）。每处改动经确认后实施；非决策项（必然派生/无取舍的实现选择）自行处理。

## 产出沉淀

- **验收标准**随规划产出（每个决策点对应验收表述；验收是流程必需）
- **spec 按需产出/更新**：轻度的、已有 spec 覆盖的修改直接更新，不询问；改动 docs/specs 结构（大幅变动/增加/删除）提前询问用户（格式见 `references/SPEC-FORMAT.md`）
- **决策沉淀**：规划确认的设计决策（难逆转/会困惑/真实权衡）→ 按项目指定的决策存放处；**新术语** → docs/CONTEXT.md（解决即写入）
- 共识后可暂停：实现任意时刻触发（`h-implement` 按任务执行，无需重新规划）。**规划共识达成后停下，不自动进入实现；实现由用户显式触发。**
